# Как работают две системы оценки поставщиков

Документ описывает пошагово работу двух подсистем — на основе **нечёткой логики**
и на основе **теории мультиопераций** — на тех же входных данных, чтобы можно
было нарисовать сравнительную схему.

---

## 0. Общие входные данные

Поставщик характеризуется временным рядом наблюдений по 3 метрикам:

| Ключ | Название | Диапазон | impact_factor | epsilon |
|---|---|---|---|---|
| `localHiring` | Наём местных жителей | 50..100 | 0.20 | +1 |
| `completeness` | Полнота заказа | 70..100 | 0.30 | +1 |
| `defects` | Дефекты | 0..30 | 0.25 | **−1** (меньше — лучше) |

Каждое наблюдение имеет:

- `month` — номер месяца (1..N)
- `date` — дата `DD.MM.YYYY`
- Три числовых значения (`localHiring`, `completeness`, `defects`)
- Три **флага качества** (`quality`):
  - `"1"` — точное значение
  - `"2"` — экспертная оценка (`?`)
  - `"0"` — значение отсутствует
  - `"3"` — неизвестно

Заключение модели — *Assessment* (тоже L↑/M↓ и т.п., с собственными параметрами трапеции).

## 0.1 База знаний (Knowledge Base)

216 правил вида:

> ЕСЛИ `localHiring = X`, `completeness = Y`, `defects = Z` ТО `assessment = W`

где `X, Y, Z, W ∈ {L↑, L↓, M↑, M↓, H↑, H↓}`.

База одна на обе системы.

## 0.2 Критерии (Criterion DB)

Для каждой из 4 переменных (3 входа + assessment) задана таблица: для каждой
комбинации (level × trend) — параметры трапециевидной функции `[p1, p2, p3, p4]`.

Например, `localHiring L↑` = `[49.9, 50, 50, 75]` — трапеция с плато на 50,
спадает к 75. `M↑` = `[50, 75, 75, 100]`, и т.д.

## 1. Система на основе нечёткой логики

### 1.1 Trim (обрезка ряда)

Нечёткая логика **не работает** с неточностями. Перед вычислениями:

1. Находим **индекс последнего «плохого» наблюдения** `lastBad` —
   у которого хотя бы одна метрика имеет `quality ∈ {"0", "2", "3"}`.
2. Берём только наблюдения **строго после** `lastBad` → `used`.
3. Метаданные обрезки: `total`, `usedObservations`, `lastBadMonth`.

**Ветки результата:**

- `used.length === 0` → **blocked**: вернуть `blockers` по последней строке
  (какие метрики неточны).
- `used.length < 2` → **blocked**: «недостаточно данных для тренда».
- Иначе → продолжаем с `used`.

### 1.2 Тренд по Pearson

Для каждой метрики на `used` считаем `r = pearson(values, months)`:

```
trend = r > -0.2 ? "up" : "down"
```

Порог −0.2 — чуть «склонён вниз»: даже слабо отрицательная корреляция уже
читается как down.

### 1.3 Активные термы (μ > 0)

Для последнего значения каждой метрики и обнаруженного тренда вычисляем
μ для **всех трёх уровней** (L, M, H) текущего направления:

```
μ_L(x) = trapezoid(x, criterionDB[L, trend].params)
μ_M(x) = trapezoid(x, criterionDB[M, trend].params)
μ_H(x) = trapezoid(x, criterionDB[H, trend].params)
```

Активный терм = тот, у которого `μ > 0`. На границе двух уровней могут быть
**два** активных терма с разными μ (например, μ_M=0.7, μ_H=0.3).

### 1.4 Cross-product → активированные правила

Перебираем все комбинации `(lh-терм × c-терм × d-терм)`, для каждой ищем
правило в КБ, у которого `level/trend` всех трёх входов совпадают. Если
правило найдено — оно «срабатывает».

### 1.5 Per-rule crisp (общий с multiop)

Для каждого сработавшего правила:

1. **Direction determinant `D`** для каждой метрики:
   ```
   D_metric = directionDeterminant(value, params, trend)
   ```
   Это знак-нагруженное число в [−1; +1], отражающее положение значения
   внутри своего терма (ближе к началу или к концу трапеции).

2. **Совокупный определитель `DA`** (взвешенный по знакам направлений):
   ```
   DA = (eps_lh · D_lh + eps_c · D_c + eps_d · D_d) / 3
   ```
   Для defects `eps = −1` (чем больше — хуже).

3. **OFN заключения `B`**: трапеция `assessment[level, trend].params`.

4. **Сдвиг `Bp = ofnShift(B, DA, assessment.trend)`**: знак `DA` тянет
   заключение в сторону «лучше» или «хуже» соседнего уровня.

5. **Defuzzify**: `crisp = defuzzify(Bp, μ=0.9)` — превращение OFN в одно
   число в [0..100].

### 1.6 Финальная оценка

```
finalScore = average(crisp_i over fired rules)
zone = classify(finalScore):
   ≤ 33.33  → red
   ≤ 66.66  → yellow
   > 66.66  → green
```

Плюс показатели: `activatedRules`, `entropy`, `trendShare`.

## 2. Система на основе теории мультиопераций

### 2.1 Подготовка параметров (`buildParametrs`)

В мультиоп для каждой метрики хранятся **два «параметра»** — на ↑ и на ↓:
`paramId` 1 = lh↑, 4 = lh↓, 2 = c↑, 5 = c↓, 3 = d↑, 6 = d↓.

**Агрегированный quality по всей истории метрики:**

```
если хоть одно q="0" → agg="3"   // источник дал нет / невалид
иначе если хоть одно q="2" → agg="2"   // часть источников = эксперт
иначе → agg="1"   // все источники = точные данные
```

**Какой параметр добавляем:**

- `agg="3"` (история имеет пропуски) → **направление неопределено**,
  добавляем **оба** параметра (↑ и ↓) с последним значением, `exactly=3`.
- `agg ∈ {"1","2"}` → определяем направление по Pearson, добавляем
  **один** параметр (↑ или ↓) с последним значением и `exactly=agg`.

### 2.2 Pearson — только для выбора направления

Pearson считается на всём ряду (если он определён). На самом значении
он не сказывается — оно всегда берётся из последнего наблюдения.

### 2.3 Проверка симптомов (`getSymptomStatus`)

Для каждого пары (параметр, симптом) симптом получает один из статусов
по модели мультиоперативного представления:

| `exactly` | Логика | Status (выход) |
|:-:|---|:-:|
| 0 | Источник не дал данных | **0** |
| 1 | Точные данные, значение в диапазоне | **2** (истинно) |
| 1 | Точные данные, значение не в диапазоне | **1** (ложно) |
| 2 | Эксперт, значение в диапазоне | **6** (истинно, источник частичный) |
| 2 | Эксперт, значение не в диапазоне | **5** (ложно, источник частичный) |
| 3 | Направление неопределено | **4** (один источник не дал значения) |

### 2.4 Метаконъюнкция area = `s_lh & s_c & s_d`

Каждое правило (area) имеет формулу `sX & sY & sZ` — конъюнкция трёх
симптомов. Применяется **метаконъюнкция** по таблице:

```
       1  2  4
   1 | 1  1  1
   2 | 1  2  4
   4 | 1  4  4
```

И обобщённая через множества для статусов 3, 5, 6, 7 (объединения базовых).

Результат — статус всей area (0..7).

### 2.5 Видимость и аггрегация

- **VISIBLE_STATUSES** = {2, 4, 5, 6} → отображаются в таблице:
  - 2 — подходит
  - 6 — может подходить (на основе доступных данных)
  - 4 — потенциально применимо (направление не определено)
  - 5 — может не подходить (по доступным данным — ложно)

- **ACTIVE_STATUSES** = {2, 4, 6} → попадают в усреднение балла.
  Status 5 «по доступным данным терм ложен» — это правило отбраковано,
  его assessment в среднюю **не идёт** (но в таблице видно).

### 2.6 Per-rule crisp (тот же, что в fuzzy)

Для каждого правила со статусом из `ACTIVE_STATUSES`:

1. Берём последние значения трёх метрик.
2. Вызываем общий хелпер `computeRuleCrisp(rule, values, ctx)` — тот же
   код, что в fuzzy: `D` → `DA` → `ofnShift` → `defuzzify`.
3. `sum += crisp.crisp`.

### 2.7 Финальная оценка

```
finalScore = sum / contributingRules
zone = classify(finalScore)
```

`contributingRules` — сколько правил попало в усреднение.
`totalActivated` — сколько правил имели любой непустой статус (для статистики).

## 3. Сравнительная схема (высокоуровневая)

```
                  ┌─────────────────────────────────────────┐
                  │     Поставщик: data[], quality[]        │
                  └─────────────────┬───────────────────────┘
                                    │
                ┌───────────────────┴────────────────────┐
                │                                        │
        ╔═══════▼════════╗                       ╔═══════▼═══════╗
        ║  FUZZY         ║                       ║  MULTIOP      ║
        ║                ║                       ║                ║
        ║ 1. TRIM:       ║                       ║ 1. Aggregate  ║
        ║   убрать       ║                       ║   quality:    ║
        ║   всё до       ║                       ║   "0"→3       ║
        ║   последнего   ║                       ║   "2"→2       ║
        ║   неточного    ║                       ║   else→1      ║
        ║                ║                       ║                ║
        ║ 2. Pearson     ║                       ║ 2. Pearson    ║
        ║   на хвосте    ║                       ║   на полном   ║
        ║                ║                       ║   ряду        ║
        ║                ║                       ║                ║
        ║ 3. μ-membership║                       ║ 3. Last value ║
        ║   для last     ║                       ║   ∈ symptom_  ║
        ║   value:       ║                       ║   range?      ║
        ║   все термы    ║                       ║   + status по ║
        ║   с μ>0        ║                       ║   exactly     ║
        ║                ║                       ║                ║
        ║ 4. Cross-prod  ║                       ║ 4. Metacon-   ║
        ║   активных     ║                       ║   junction по ║
        ║   термов       ║                       ║   3 симптомам ║
        ║                ║                       ║                ║
        ║ 5. computeRule ║◄──── shared ─────────►║ 5. computeRule║
        ║   Crisp        ║      function         ║   Crisp       ║
        ║                ║                       ║                ║
        ║ 6. Average →   ║                       ║ 6. Average →  ║
        ║   finalScore   ║                       ║   finalScore  ║
        ╚════════════════╝                       ╚═══════════════╝
                │                                        │
                └───────────────┬────────────────────────┘
                                ▼
                       Две независимые оценки
                       (зона + балл)
```

## 4. Где системы расходятся

| Аспект | Fuzzy | Multiop |
|---|---|---|
| Данные | только точный хвост | весь ряд |
| Pearson | по хвосту | по полному ряду |
| Принадлежность | трапециевидная μ ∈ [0;1] | булева: `value ∈ range`? |
| Граничные значения | μ может быть 0 на границе | range-check включает границу |
| Активация правил | μ_lh × μ_c × μ_d > 0 | s_lh & s_c & s_d ≠ 0/1 |
| Неопределённость | блокировка, если в хвосте есть | status 4 в area, продолжаем |
| Эксперт в last | блокировка | status 5/6 |
| Финальная агрегация | **одна и та же**: средний defuzzified crisp | **одна и та же** |

---

## 5. Где системы сходятся

Если входные данные **полностью точные**, активированные fuzzy-правила и
multiop-правила со status=2 — это **один и тот же набор**, и финальный
балл идентичен (см. кейсы 01–05, 13 в `test-cases/`).

Это инвариант: «на точных данных обе системы дают тот же результат».
